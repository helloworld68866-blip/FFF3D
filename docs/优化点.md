有，而且从你这份 `95.zip` 代码看，**最大的效率优化不在某个公式或循环小改，而在“热路径对象模型 + 临时内存生命周期 + 求解器装配生命周期”这三块**。

我静态扫了一遍项目：`src` 里大约 146 个 C++/hpp 文件、4.4 万行左右；其中 `src/hydro/driver/static_grid_hydro.cpp` 单文件约 7000 行，是目前最明显的性能和维护热点。整体架构方向是对的：已经在往 DEC3D 应有的分模块推进、macro-zoning、HLLC/PPM、HYPRE 隐式扩散方向靠。论文/手册里强调 DEC3D 的核心就是显式水动力与隐式热/辐射/alpha 分步推进，并用 macro-zoning 放宽球坐标 CFL 限制、用 HYPRE 解大规模非对称扩散系统。fileciteturn2file0 但你现在的代码还有不少“实现层面拖慢架构”的地方。

## 最高优先级：去掉 hydro 热路径里的动态 `std::vector`

最值得先改的是 `HydroConservativeState` / `HydroPrimitiveState` 里的：

```cpp
std::vector<double> radiation_chi;
```

这类状态对象在 HLLC、PPM、通量计算、单元加载、状态转换里会被大量创建、复制、缩放、相加。现在 `static_grid_hydro.cpp` 里的 `LoadCellState` 会为每个 cell 构造 radiation vector；`hllc_solver.cpp` 里的 `ScaleBundle`、`AddBundle`、`SubtractBundle`、`BuildStarState`、`ComputePhysicalFlux` 又会继续复制/返回这些 vector。只要 radiation group 数量不是 0，这会造成大量小对象分配和内存搬运。

**建议改法：**

把 hydro 主状态收缩成固定标量状态，例如：

```cpp
struct HydroCoreState {
    double rho;
    double mom_r, mom_theta, mom_phi;
    double total_energy;
    double electron_chi;
    double alpha_chi;
};
```

radiation group 不要塞进每个 Riemann state，而是作为单独的 SoA 数组批量平流：

```cpp
std::vector<Array3D<double>> radiation_chi_groups;
```

也就是说：HLLC 只负责核心流体波系；电子标量、alpha、radiation group 作为 passive scalar bundle 按已有质量通量/速度场更新。这样能显著减少 per-interface 动态分配。

这是我认为**收益最大、风险中等**的一项。它会动到接口，但物理意义清楚，而且和 DEC3D “电子压强标量平流”的设计是一致的。论文也明确把电子压强的 \(P_e^{3/5}\) 作为标量平流方程处理。fileciteturn1file0

## 第二优先级：给 hydro step 做持久 scratch workspace

`static_grid_hydro.cpp` 现在有很多每步、每条线、每个方向都会重新分配的临时数组，比如：

- `BuildSnapshotArray(snapshot)`
- `CaptureSnapshot(hydro_view)`
- `radial_ppm_lines`
- `ghosted_line`
- `effective_widths`
- `line_reconstruction`
- `interface_fluxes`

尤其 `radial_ppm_lines` 会保存大量径向线工作区，内存占用和分配次数都会很高。

**建议改成：**

```cpp
struct HydroScratch {
    std::vector<HydroCoreState> ghosted_line;
    std::vector<double> effective_widths;
    std::vector<FluxState> interface_fluxes;
    PpmLineReconstruction reconstruction;
    Array3D<FallbackMask> fallback_mask;
    Array3D<HydroCoreState> snapshot; // 必要时才分配
};
```

每个 rank 初始化一次，之后每步复用。  
对 radial shell-wide fallback，建议改成两遍流式处理：

1. 第一遍只算 fallback mask；
2. 第二遍重建当前 line，立即累加 flux，不保存所有 radial PPM line。

这会减少大量内存分配和 cache miss，也能让 OpenMP/MPI 之后更容易加。

## 第三优先级：把 diagnostics / budget 检查从生产路径剥离

当前 hydro result 和 driver 里有很完整的 timing、budget residual、stage diagnostic、字符串报告，这对调试很有用，但生产跑高分辨率时会拖慢。`BuildBudgetResidualSummary` 这类函数会再扫一遍全域；`ostringstream` 也在很多文件里频繁出现。

建议引入运行模式：

```cpp
enum class RuntimeMode {
    ContractTest,
    Debug,
    Production
};
```

生产模式下默认关闭：

```cpp
compute_budget_residual = false;
collect_stage_diagnostics = false;
format_report_strings = false;
```

只保留必要 reduction 和 timer。  
建议每 N 步抽样一次 budget，而不是每步全量扫描。

## 第四优先级：HYPRE 求解器上下文持久化

`src/transport/diffusion/hypre_distributed_diffusion_solver.cpp` 目前倾向于每次 solve 都创建/销毁 IJMatrix、IJVector、GMRES、BoomerAMG，并逐行组装矩阵。对热传导、辐射、alpha 这类反复求解的扩散问题，这个开销很可观。

论文里 DEC3D 的隐式热/辐射/alpha 都是大规模 sparse nonsymmetric 系统，并使用 AMG 预条件 GMRES；macro-zoning 主要服务显式 hydro，隐式模块仍在 fine mesh 上求解。fileciteturn1file7 所以这里应当把“矩阵图结构”和“求解器对象”尽量复用。

建议加：

```cpp
class DistributedDiffusionSolverContext {
public:
    void initialize_pattern(const DistributedGrid& grid);
    void update_values(const DiffusionCoefficients& coeff);
    void update_rhs(...);
    void solve(...);
};
```

优化点：

- row partition、邻接 pattern、column indices 只初始化一次；
- 每步只更新 matrix values 和 RHS；
- `std::vector<HYPRE_BigInt> columns` / `std::vector<HYPRE_Complex> values` 不要每行重新分配；
- 尽量批量 `HYPRE_IJMatrixSetValues`，不要一行一行临时构造 vector；
- 每个物理模块或每个 radiation group 维护自己的 context。

这项收益很高，尤其 radiation group 多的时候。

## 第五优先级：几何量缓存

球坐标代码里会反复计算：

- cell volume；
- radial/theta/phi face area；
- effective width；
- \(r^2\)、\(\sin\theta\)、\(\cos\theta\)；
- inverse volume。

这些在 hydro flux、diffusion assembly、macro-zoning 里都会用。现在不少几何函数是在循环内部即时算的。建议加一个随 mesh version 更新的缓存：

```cpp
struct GeometryCache {
    std::vector<double> r_center, r_face;
    std::vector<double> theta_center, theta_face;
    std::vector<double> sin_theta_center, sin_theta_face;
    Array3D<double> volume;
    Array3D<double> inv_volume;
    Array3D<double> dr_eff, dtheta_eff, dphi_eff;
    Array3D<double> face_area_r, face_area_theta, face_area_phi;
};
```

动网格只沿径向变，所以不需要每个 stage 都重建所有角向几何量。  
这项风险低，收益稳定。

## 第六优先级：`Array3D` 内层访问不要默认 bounds-check

`Array3D<T>::operator()` 现在如果内部用 `storage_.at(...)`，再加上 `linear_index` 手动检查，内层循环会反复做边界检查和异常路径准备。这对 hydro/diffusion 热循环很不友好。

建议分成两套接口：

```cpp
T& operator()(int i, int j, int k) noexcept;       // release 热路径，无检查
T& checked(int i, int j, int k);                   // 测试/调试使用
```

同时暴露：

```cpp
T* data() noexcept;
size_t linear_index_unchecked(...) noexcept;
```

这样后面做 SIMD、OpenMP、批量序列化也更容易。

## 第七优先级：radiation group 并行化

多群辐射每个 group 的扩散 solve 在能量回写前基本是独立的。手册和论文架构也把多群辐射作为 group-wise implicit diffusion 处理。fileciteturn2file0

如果你以后跑 12-group 或更多 group，建议：

- 小规模：rank 内用 OpenMP/task 并行 group solve；
- 大规模：MPI communicator 按 group split，让不同 rank 子集解不同 group；
- solve 完以后只做一次 group energy exchange reduction/update。

这项不一定马上做，但如果 radiation 开起来，它会变成主要加速点。

## 第八优先级：输出/重启改成 rank-sharded binary

现在输出/重启如果大量使用 CSV/text 或 root gather，全分辨率时会很慢，也会让 root rank 成为瓶颈。建议保留 CSV 给小测试，但生产路径用：

```text
checkpoint.stepXXXX/
  meta.json
  rank0000.bin
  rank0001.bin
  ...
```

每个 rank 写自己的 slab，restart 时每个 rank 读自己的文件。  
如果愿意引入依赖，HDF5/ADIOS2 更标准；不想引依赖，自己写简单 binary header 也够用。

## 第九优先级：构建模式明确区分 debug / production

CMake 里建议明确加生产配置，而不是只靠默认编译选项：

```cmake
-DCMAKE_BUILD_TYPE=RelWithDebInfo
-O3
-DNDEBUG
-march=native   # 本机/专用集群可开
-flto           # 视编译器和依赖情况
```

`-ffast-math` 不建议默认开，因为你这里有守恒、正性、CFL、EOS/输运系数等敏感逻辑；可以单独做一个 experimental target，跑完 shock tube、clean implosion、thermal slab 回归后再判断。

## 我建议的实施顺序

先不要直接动 HYPRE 或 MPI。最稳的顺序是：

1. **先加 profiling/timing 粒度**：确认 hydro、diffusion assembly、HYPRE solve、IO 各占多少。
2. **先改 hydro state 的 `radiation_chi` 动态 vector**：这是最像“架构性性能 bug”的点。
3. **再做 `HydroScratch` 复用和 radial line 流式化**。
4. **再把 diagnostics/budget 从 production path 剥离**。
5. **最后做 HYPRE context 复用和 radiation group 并行**。

一句话判断：你现在代码的大方向是 DEC3D 正统架构，但实现层面还偏“正确性优先的科研原型”。如果要提速，第一刀应砍掉 hydro 热路径里的动态对象和反复临时分配；第二刀才是 HYPRE/辐射并行；第三刀是 IO 和 diagnostics。
